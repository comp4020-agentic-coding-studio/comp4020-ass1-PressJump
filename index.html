Eight agents, one repo

Pointing a bunch of coding agents at the same repository feels like it should get you a bunch of times the speed. In practice it doesn't, because they all end up wanting the same working directory. And the obvious fix, giving each agent its own worktree, quietly isn't enough on its own either. The missing half is a shared build cache, and this page is a little simulation you can poke at to see why.

Skip to the simulator ↓

Every agent runs the same loop

Before comparing setups, it helps to know what one agent's work actually looks like. Each simulated agent works through three tasks, and every task has the same shape, plan → edit → build → test. Two of those steps are greedier than they look. Editing and testing need the working tree, the actual files on disk, and no two agents can safely hold it at once. Building needs a CPU core, a build output and a warm cache. The first build after a cache goes cold pays a heavy penalty to recompile the world.

As you're reading the timelines below, real work is coloured, wasted work is hatched red, and waiting shows up as a dotted line.

Setup 1 · one shared checkout

This is the default nobody really chooses, everyone just working in the same checkout. Rather than crashing into each other, the agents end up queueing, and you can see the rows below politely taking turns. Every handover is a branch switch that costs a little time and, rather worse, dirties the build cache, so almost every build ends up running cold. Adding another agent doesn't add any throughput here, just a longer queue, and the wall clock keeps growing with every agent you add.

Setup 2 · a worktree each

The fix most people reach for is running git worktree add and giving each agent its own checkout. The queue disappears and things get a lot faster, which is usually where the story ends. Looking a little closer at the timeline, though, there's a lot of heat. Every worktree starts out empty, so every agent ends up paying the cold build that the shared checkout at least occasionally avoided. All that hatched red is the same world being recompiled once per agent, and once you're past your core count it starts landing back on the wall clock.

Setup 3 · worktrees plus a shared build cache

The half nobody really talks about is keeping the isolation while sharing the cache. This is the recipe products like Hyperlane are built around, and there are alternatives out there too, from other agent runners to wiring it up yourself with git worktree plus whatever cache your ecosystem speaks (ccache, sccache, Bazel, Turborepo). With the cache shared, exactly one build in the whole system runs cold, and running it warms the cache for everyone else, leaving the rest doing only their own incremental work. You might notice the wall clock merely ties setup 2 at four agents, so the win is hiding in the missing red. Heading down to the lab and cranking the agent count is where the gap really opens up.

There's a quieter cost hiding in all this isolation too, and that's disk space. Giving every agent a full copy of the checkout, the dependencies and the build output adds up fast. Folder syncing along the lines of AFD helps here, sharing one base folder underneath all the worktrees while keeping only each agent's own modifications in its isolation. Eight agents end up costing you one base plus eight small piles of changes rather than eight full copies, so the space isn't wasted either.

The takeaway

Isolation takes care of the queue, and the shared cache takes care of the cold tax. You really do need both, and almost every "run more agents" setup out there ships with only the first, or with neither. Whether that means picking up the whole recipe off the shelf, Hyperlane being one product built around it, or assembling it yourself from the pieces named above, at least now you know what to look for.

If there's one habit worth taking away from all this, it's going looking for the resource nobody wrote down whenever parallelism disappoints. Here it happened to be the working directory and the build cache. In your system it will be something else with the same shape.

All durations are abstract time units, deliberately unmeasured placeholders, each marked TODO(measure) in src/model.ts. The claim is the shape of the story, not the seconds. The scheduler is deterministic, busy time comes out identical across all three setups, and only wasted and blocked time differ.
